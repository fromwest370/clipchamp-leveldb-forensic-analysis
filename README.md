# Clipchamp LevelDB Forensic Analysis

## 概要

このリポジトリで実際に動作するツールは  `clipchamp_filename_extractor.py`  です。
Clipchampの削除済みプロジェクトが残すLevelDBログから、使用されていた動画ファイル名と
その出現回数をワンコマンドで抽出できます。

以下は、そのツールを作るに至った2か月間のバイナリ解析の記録と、技術的な限界点のまとめです。

---

## 1. 課題

Clipchampで誤って削除したプロジェクトについて、ローカルに残っているLevelDBログからプロジェクト情報を復元できないかを調査した。

目的は、単なる動画ファイルの救出ではなく、**プロジェクトのタイムライン、素材参照、インデックス構造を再構築してClipchampプロジェクトとして復元すること**だった。

---

## 2. 分かったこと

LevelDBログから、プロジェクトで使用された素材と考えられるMP4ファイル名を確認した。

### recovered_filenames.csvで確認した実測値

| ファイル名 | 出現回数 |
|---|---:|
| `P1001015.mp4` | 55 |
| `P1001016.MP4` | 50 |
| `P1001017.MP4` | 50 |
| `P1001018.MP4` | 50 |
| `P1001019.MP4` | 40 |
| `P1001024.mp4` | 5 |
| `P1001025.MP4` | 10 |
| `P1001027.MP4` | 40 |

合計8種類、**300件**のファイル名出現を確認した。

また、LevelDB内部には `assetId`、`fileName`、`permanentUrl`、`local-cache/<UUID>` などの情報が存在し、素材とAsset IDの対応を追跡できることを確認した。実データには、例えば `P1001015.MP4` と対応するAsset ID `8ea956ca-46af-432c-a0be-695b735250b2`、`P1001027.MP4` と対応するAsset ID `6dde8f01-c758-45f0-8395-b90bb496b16e` が確認できる。

タイムラインについても、素材ごとのduration候補を抽出し、既知のTimeline durationとの完全一致を照合する解析を実施した。ただし、この照合では**既知のTimeline durationとの完全一致は確認できなかった**。したがって、ここでの成果は「一致を発見したこと」ではなく、候補値を抽出して既知値との照合作業を行ったことにある。Notebook上では `startTime`、`duration`、`endTime`、`position`、`offset`、`speed`、`from`、`to` などを候補として抽出している。

### 追加で確認できたバイナリ構造

以下は解析途中で実測した構造である。ただし、**Clipchamp内部での正式な意味までは確定していないものについては「構造上の確認」に留める**。

- `32 02 XX` を含む反復構造を確認
- `93 00 01` → 4-byte VALUE → 固定部分 → 次の `32 02 XX` という配置を確認
- `32 02 XX` から次の同型構造まで、X1～R5では49 bytes、R6では53 bytesという差を確認
- UTF-16LEの `https://app.clipchamp.com/local-cache/...` URLを実データから境界付きで確認
- 同一レコード内だけでなく、別Assetを参照していると考えられるクロスアセット構造を確認

### 技術的詳細の根拠

これらの数値は、最終Notebookの「Cell番号」ではなく、解析を段階的に記録した `R###` の検証ステップ番号で確認したもの。

| 内容 | 根拠 | 確認内容 |
|---|---|---|
| `32 02 XX` がCOMMON内11回 | **R758** | R3～R6の各COMMON範囲で `32 02 XX` を11回検出 |
| 49 / 53 bytes | **R801** | X1～R5=49 bytes、R6=53 bytes |
| `93 00 01`構造が6件 | **R796** | X1～R6の6箇所で同一配置を検出 |
| URL 73文字 / 146 bytes | **R767** | UTF-16LE URLの実境界を確認 |
| CRC32C整合性 | **R508 / R509** | 6レコードについてCRC整合性とレコード長を確認 |

ただし、現在参照できる解析記録からは、これら `R###` 番号を**Jupyter Notebookの正式なCell番号として対応付けることはできない**。したがってREADMEでは「Cell Xで確認」とは表現せず、実際の解析記録に残っている `R###` ステップ番号を根拠としている。

また、`32 02 XX` や `93 00 01` の**意味（ID、インデックス等）そのものは確定していない**ため、READMEでは意味を断定しない。

## 3. 手法の要約

### ① LevelDBログをバイト列として読む

Pythonでバイナリログを `bytes` として読み込み、絶対バイト位置を基準に解析した。

### ② 既知文字列を起点に構造を特定

`fileName`、`filename`、MP4ファイル名、`assetId`、`permanentUrl`、`local-cache` URLなどを検索し、前後のバイト列を比較した。

実データでは `fileName`、Asset ID、ファイルハッシュ、動画metadata、durationなどがまとまって格納されていることを確認した。

### ③ レコード間の差分比較

R1～R6など対応する構造を横並びにして、

- 固定バイト
- 可変バイト
- 相対位置
- 反復回数
- 構造長

を比較した。

### ④ ASCII / UTF-16LE解析

通常のASCII文字列だけでなく、Clipchamp内部で使用されているUTF-16LEのURL・ファイル名を解析した。

### ⑤ バイト単位の構造検証

`32 02 XX`、`93 00 01`などのバイトパターンを起点として、周囲の固定・可変フィールド、相対位置、繰り返しを確認した。

### ⑥ CRC整合性確認

LevelDBレコードについてCRC32Cを用いた整合性確認を行った。

## 4. 限界点

最大の問題は、

**「データが残っている」ことと「Clipchampがプロジェクトとして再構築できる」ことは別問題**

だった点にある。

ファイル名、Asset ID、URL、動画metadata、duration候補などは確認できたが、削除前のプロジェクトを構成していた全インデックスを一意に再構築することはできなかった。

特に、

- 内部ID同士の正式な意味
- タイムライン要素とAssetの完全な親子関係
- インデックスの完全な対応関係
- 削除前の全オブジェクト状態
- 各バイナリVALUEの正式な意味

については、実測データだけでは確定できない部分が残った。

したがって、今回の結論は、

> **素材・Asset・URL・バイナリ構造をかなり深く特定できたが、Clipchampが読み込める完全なプロジェクトインデックスの再構築には至らなかった。**

である。

これ以上のバイナリ解析・インデックス復元は、この時点で中断する。

## 5. 成果物

### `clipchamp_filename_extractor.py`

LevelDBなどのバイナリファイルから、`Pxxxxx.mp4`形式のファイル名を抽出するスタンドアロンPythonツール。

機能：

- ASCII形式のファイル名を検索
- UTF-16LE形式のファイル名を検索
- ファイル名ごとの出現回数を集計
- バイト位置を表示
- 外部ライブラリ不要
- 元ファイルを読み取り専用で処理

実行例：

```bash
python clipchamp_filename_extractor.py "C:\path\to\000212.log"
```

このリポジトリは、

**「Clipchampを復元できた」という成功事例ではなく、削除されたプロジェクトを対象に、PythonでLevelDBバイナリを解析し、実際にどこまで情報を回収でき、どこで技術的限界に達したかを示すポートフォリオ**

- Python
- バイナリファイル処理
- `bytes` / hexadecimal解析
- 正規表現
- ASCII / UTF-16LE文字列解析
- LevelDBログ構造の調査
- CRC32C整合性確認
- バイト単位のdiff
- レコード間構造比較
- CSVによる解析結果整理
- Jupyter Notebookによる段階的検証

完全復元に失敗したことを隠すのではなく、

1. 問題設定

3. 仮説設定
4. Pythonによる検証
5. バイト単位の構造比較
6. Asset / filename / URLの対応付け
7. 技術的限界の判断

という問題解決プロセスを示す。

なお、GitHubへ公開する際は、元のClipchampログ、個人データ、ファイルハッシュなどをそのまま公開せず、解析コードと匿名化したサンプル出力のみを公開する。
